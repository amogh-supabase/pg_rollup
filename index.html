Architecture

Bi-temporal by default.

Every rollup tracks two timelines — when an event happened in the source, and when each rollup version was the truth. Query either, or both.

As-is

The truth right now.

A regular view filtered to _is_current. Drop-in for any dashboard query — no version metadata visible, no joins to remember.

source → refresh() → rollup.<name>
Object: View
Latency: Index lookup
Cost: Free
As-was

The truth back then.

Each refresh closes affected buckets and inserts new rows with _version_from / _version_to markers. Replay the rollup at any historical timestamp.

_version_from → _at(t) → _diff(t1, t2)
Object: Generated function
Retention: Configurable
Cost: One INSERT per change
Capabilities

Everything a rollup should do.
Without an extension.

Pure SQL. Pure PL/pgSQL. The whole library installs into one schema and runs on stock PostgreSQL — managed, self-hosted, embedded, doesn't matter.

Versioned refresh

Old values are closed, new values inserted. Every refresh becomes part of the audit trail.

Point-in-time _at()

Typed table function returning the rollup state at any timestamp. Reconstructs exactly what the dashboard showed then.

Change _diff()

Compare two timestamps. One row per (bucket, group) with _a / _b columns plus a change_type marker.

Incremental refresh

Scans only the recent window via a high_water_mark plus lookback. Idempotent — no churn when nothing changed.

Late-arriving data

A lookback window catches recent updates automatically. refresh(since := ...) for older targeted rescans.

Arbitrary aggregates

Pass through any SQL: count(*) filter, percentile_cont, math, nullif. Column types probed automatically.

Optional scheduling

schedule := '* * * * *' wires into pg_cron. Skip it and refresh manually — or from any external scheduler.

Batched backfill

CALL rollup.backfill(...) is a procedure that commits between batches — a 10M-row initial load won't hold one giant transaction.

Workflows

What's true now.
What was true then.

The current view answers as-is. The generated _at() and _diff() functions answer as-was. Any data engineer can write a rollup — pg_rollup writes the version history.

Query the current view

The rollup is a regular view, filtered to the most recent version of each bucket. Drop-in for any query, dashboard, or CSV export — no version metadata to think about.

  • Same column shape as the source aggregation
  • Materialized for fast reads
  • Refreshes on schedule or on demand
  • One row per (bucket, group) combination
As-is 
-- Top trading categories over the last 30 days
SELECT bucket::date, item_category,
       trade_count,
       total_volume_gp
  FROM rollup.ge_daily_by_category
 WHERE bucket > now() - interval '30 days'
 ORDER BY total_volume_gp DESC
 LIMIT 10;

A trade lands weeks late

A Twisted Bow auction settles weeks after the dashboard was first compiled. pg_rollup's lookback window automatically catches it on the next refresh, closes the old bucket, and inserts a new version with the corrected value.

  • Default lookback: bucket_size × 3
  • Custom since := for older targeted rescans
  • Old version preserved with _version_to
  • New version becomes current automatically
Late arrival 
-- One Twisted Bow trade lands late
INSERT INTO ge_transactions (
    player_name, item_name, item_category, txn_type,
    quantity, price_per_unit, world, is_members, traded_at
) VALUES (
    'Zezima', 'Twisted Bow', 'Weapons', 'sell',
    1, 1100000000, 301, true,
    '2024-12-20 14:30:00+00'
);

-- Next refresh closes the old bucket, inserts new
SELECT rollup.refresh('ge_daily_by_category');

Reconstruct any moment in the past

Every rollup gets a generated <name>_at(timestamp) function. Passing a historical timestamp returns the rollup exactly as it existed at that moment — what the dashboard would have shown to anyone querying it.

  • Type-safe return: same shape as the view
  • Predicate: _version_from ≤ t < _version_to
  • Works for any timestamp in the version history
  • Bounded by purge_history() retention
As-was 
-- What did the rollup show last Wednesday at 9 AM?
SELECT bucket::date, item_category,
       trade_count, total_volume_gp
  FROM rollup.ge_daily_by_category_at(
         '2024-12-18 09:00'::timestamptz)
 ORDER BY total_volume_gp DESC;

-- Compare the same week of trades to a snapshot
-- from 24 hours earlier
SELECT *
  FROM rollup.ge_daily_by_category_at(
         now() - interval '24 hours')
 WHERE item_category = 'Weapons';

Explain exactly what changed

<name>_diff(t1, t2) compares two as-was snapshots row-by-row. Each row carries the bucket key, paired _a / _b values for every aggregate, and a change_type — find the exact buckets that drove a number change.

  • change_type: added, removed, changed, unchanged
  • One row per (bucket, group) tuple
  • Compute deltas in SQL: total_b - total_a
  • Filter WHERE change_type <> 'unchanged' for surprises
Diff 
-- What changed between yesterday's snapshot and now?
SELECT bucket::date,
       item_category,
       trade_count_a,    trade_count_b,
       total_volume_gp_a, total_volume_gp_b,
       (total_volume_gp_b - total_volume_gp_a) AS delta,
       change_type
  FROM rollup.ge_daily_by_category_diff(
         now() - interval '24 hours',
         now())
 WHERE change_type <> 'unchanged'
 ORDER BY abs(total_volume_gp_b - total_volume_gp_a) DESC;
Production Safety

Built to never lie.

Every refresh is atomic. Every version is preserved. Storage growth is bounded. Installation can't break your database because there's nothing to break.

Transactional refresh

One BEGIN/COMMIT per refresh. Mid-flight failure rolls back everything, including the log row.

BEGIN … ROLLBACK ON ERROR

Smart close-and-insert

Buckets whose values didn't change keep their existing row. No-op refreshes don't pollute the version table.

unchanged → skip

Bounded history

purge_history(older_than) deletes only closed versions. Current rows are never touched.

closed AND _version_to < cutoff

No-superuser install

Pure user-space SQL. No CREATE EXTENSION, no shared_preload_libraries. The anti-extension.

Get Started

Three steps to versioned rollups.

Requires PostgreSQL 15+. Optional: pg_cron, if you want scheduled refreshes. No compilation, no agents, no config files.

01

Install

Clone the repo and run install.sql. Takes under a second on an empty database.

psql "$PGROLLUP_DB" -f install.sql
02

Create a rollup

One function call. The source schema is introspected; aggregate types are probed from a LIMIT 0 query so anything valid in SELECT ... GROUP BY works.

SELECT rollup.create(
    name        := 'ge_daily_by_category',
    source      := 'ge_transactions',
    time_column := 'traded_at',
    bucket_size := interval '1 day',
    groups      := ARRAY['item_category'],
    aggregates  := ARRAY[
        'count(*) as trade_count',
        'sum(total_gp) as total_volume_gp',
        'count(distinct player_name) as unique_traders'
    ],
    schedule    := '*/5 * * * *'     -- optional pg_cron
);
03

Query, time-travel, diff

The view shows current truth. _at() replays history. _diff() shows what changed.

-- Current truth
SELECT * FROM rollup.ge_daily_by_category;

-- Reconstruct last Wednesday morning
SELECT * FROM rollup.ge_daily_by_category_at('2024-12-18 09:00');

-- Compare two snapshots, find what changed
SELECT * FROM rollup.ge_daily_by_category_diff(
    now() - interval '24 hours', now())
 WHERE change_type <> 'unchanged';
